## Approval and effect boundary

The native controller accepts requests only from `main`, with strict bounded object envelopes. It
recognizes the internal `board.attach-delivery` permission and only the `attachDelivery` operation;
no public TypeScript permission, Tauri command or package method is added in this slice. The existing
installation-generation mechanism is reused for both document and task selections.

A pending selection binds request identity, recipient/version/generation, purpose, operation, limit
and restore epoch. The host supplies approved `{id, revision}` references from the displayed task
list. Commit requires the same current task versions and records canonical titles. It never stores
task descriptions, sources or execution state in the returned grant. Cancel/expiry creates no grant.
The first valid commit attempt freezes the selected references, including when its durable write
fails; retry cannot replace or expand them. A successful exact retry returns the original grant,
even if its task subsequently changed. That old grant then fails new effect authorization as stale.

Durable grant metadata is stored in the task board's native `taskGrants` ledger. Ordinary renderer
writes discard their supplied copy and preserve the current native ledger, just like existing create
receipts. Grant issuance/revocation and task revisions use the existing atomic board save. These
metadata-only writes leave card revisions unchanged. Pending sessions expire after 15 minutes and
are capped at 16; grants are capped at 1,024 total, 256 per package and 2 MiB serialized metadata.
Each selection permits 1–50 distinct tasks; revisions must be positive safe integers. Revoked records
remain retained; capacity failure does not silently evict or revive earlier grants.

The effect-side authorization function requires a native-owned invocation context, a freshly loaded
validated board, and the caller's task-data/authority fences held through the eventual effect. It
checks current permission and installation, grant revocation, restore epoch, exact item/revision and
the requested operation. Another package, another task, acceptance, delegation, reading and arbitrary
updates are denied. C04b2 must consume this check inside its transaction; this receipt does not claim
an attachment mutation is available yet.

## Restore and lifecycle

`task-grant-epoch.json` is generated with native randomness and durably replaced under `task-data.lock`.
It is deliberately outside backup roots. Restore rotates it before replacing user data; interrupted
restore recovery rotates it before restoring the rollback copy. Restored grants can remain as records
but cannot regain authority, including when an archive predates revocation or originates elsewhere.
Missing epoch state fails authorization; a new picker creates a new epoch for fresh approvals.

Grants survive an ordinary restart because the installation generation and restore epoch persist.
Pending sessions do not survive restart. Disable/re-enable, update, same-version reinstall and removal
of the requested permission invalidate existing grants and pending approvals. Authority checks read
the current native registry under its fence, rather than relying on cached renderer state.

## Verification

The initial five-test run failed because the native contract did not recognize the new permission;
the final suite exercises approval behavior rather than treating that admission failure as evidence
of the later invariants. Eleven focused native tests now cover:

- Host-only issuance, metadata-only results, same-request retry and dismissal/expiry.
- Changed displayed versions, malformed objects/array-shaped references, unknown fields, duplicate
  tasks, forbidden operations and pending-session limits.
- Cross-package/item denial, wrong revisions, unrelated-card stability, stale-task rejection and
  revocation; failed checks preserve task-board bytes.
- Precommit I/O failure, frozen retry input, one retained grant and ignored renderer ledger forgery.
- Restart retention, disable/re-enable, update, reinstall and permission removal.
- Restore after revocation, foreign backups, interrupted restore refusal/recovery and epoch exclusion
  from backups. Native data maintenance refuses commit/list/revoke without task effects.
- Durable grant capacity and malformed-backup rejection.

A bounded independent source review found no concrete authorization, locking, restore or ledger-loss
issue under the stated caller/locking contract. Final `cargo test --manifest-path src-tauri/Cargo.toml`
passes **221 top-level tests**, plus one nested profile child; two existing live-agent tests remain
ignored. `npm test` passes **175 platform + 5 capability tests**. Logs:
`/tmp/nooki-c04b1-native-final.log`, `/tmp/nooki-c04b1-js.log`.

The rebuilt installed binary passes a separate synthetic ledger smoke through its real worker socket:
valid ledger read, ignored renderer forgery, affected-task revision advance, restart retention,
array-shaped-grant refusal and clean worker exit. The [state receipt](C04b1-installed-state.json)
includes the installed executable hash. This deliberately seeded ledger test proves native persistence
integration; the Rust tests above prove approval/authorization. Neither is public picker/UI acceptance.

Desktop build/install and `codesign --verify --deep --strict /Applications/Nooki.app` pass. The bundle
is 24.66 MiB (release compilation: 29.98 seconds); the existing large-chunk advisory remains. No personal data or live agent was used.
The legacy shared-realm package loader remains trusted-only pending R02/R03/K4.
