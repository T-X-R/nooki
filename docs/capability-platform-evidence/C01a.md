## Delivered behavior

`PlatformState` now owns a bounded invocation-authority store. A trusted native controller can
explicitly grant the first board-create scope to a native caller and an enabled installed package
at the expected version. Calling this Rust-only issuance method is the host grant decision; it is
**not** a package-callable permission request, and it is not exposed as a Tauri command. C01c must
connect issuance to the actual trusted controller, manifest/approval policy and native caller binding.
There is no new SDK or renderer API in this increment.

Opaque invocation handles contain 32 bytes of system randomness. The existing locked `getrandom`
0.3.4 crate is made a direct dependency; no crate version is upgraded. Randomness failure refuses
issuance, with no timestamp or other predictable fallback. At most 16 handles per package and 256
across the store are retained; explicit revocation or lifecycle invalidation returns capacity.

An admitted operation must match the stored native caller, `board.create` operation and `board`
resource scope. Its package ID/version and installation generation come from native state, not a
caller-supplied request. Unknown handles, a different caller, a different operation or a different
resource fail before the supplied effect callback runs. The current resource scope authorizes
creating an item; it grants neither existing-item access nor delegation.

The private registry persists an opaque installation generation. Install, update, external package
replacement/rollback, enable/disable and uninstall all go through one registry commit path, replacing
or removing that generation and invalidating only that package's handles. Old registry files lacking
the field still load; their first native grant creates a generation atomically. Live invocation
handles remain memory-only and are never restored after application restart.

## Effect ordering and persistence

The synchronous authority check holds the registry read lock and authority mutex through the short
local effect callback. Registry transitions take the registry write lock before the authority mutex;
direct revocation uses the authority mutex. Thus an already-admitted local effect finishes before
revocation returns, and subsequent callbacks cannot run with the revoked handle. The effect must
not re-enter PlatformState or await another process. This is not a claim about worker-side writes:
C01b must coordinate those with lifecycle state across the native IPC/process boundary.

Registry commits write and sync a temporary file before rename. After rename, in-memory state and
handle invalidation advance together; the parent directory is then synced on Unix. A failure before
rename preserves the original registry and live handles. If the final directory durability
acknowledgement fails, the visible state remains advanced and the operation reports `OUTCOME_UNKNOWN`
rather than falsely restoring the old authorization in memory. The post-rename failure branch is
source-reviewed, not fault-injected in this receipt.

The system random source is portable, and directory syncing is conditional on Unix so the old
non-Unix installation path is not replaced by a `/dev/urandom` dependency or directory-open failure.
Only the macOS behavior is tested here; no new Windows/Linux support or durability claim is made.

## Verification

The first four tests failed against explicit unimplemented methods before implementation
(`/tmp/nooki-c01a-red.log`). The final authority suite has eight tests covering:

1. Native caller/scope/unknown-handle refusal before effects; stored package/version provenance.
2. Disable/re-enable, update, uninstall/reinstall and restart never revive old handles.
3. Per-package capacity refusal and release after revocation/disablement.
4. Synchronized admitted effect versus **both direct revocation and disablement**; late callbacks fail.
5. Injected pre-rename write failure preserves exact registry bytes, generation and the live handle.
6. External package update and rollback invalidate both prior generations' handles.
7. Legacy-registry generation migration and an ordinary failed effect without corrupted authority.
8. The 256-handle aggregate limit, package-specific invalidation and unaffected peer handles.

The independent adversarial review identified missing direct-revocation race coverage. The test
now exercises it separately from disablement's registry-lock path. No unrelated policy engine,
permission vocabulary or user-facing feature was added to satisfy the tests.

The first full native run was blocked by sandbox `EPERM` for the local relay socket and worker
startup. That run is retained as `/tmp/nooki-c01a-native-regression.log`; it is not counted as a pass.
The same suite was rerun with local IPC permitted. Final code and delivery checks are recorded below.

## Remaining C01 work

C01a does not create a board item, persist an idempotency receipt, enforce a worker-process transaction,
or expose a public Host operation. C01b owns the atomic board effect/receipt and cross-process
revocation check; C01c owns the trusted issuance path, canonical errors/contract, exported kit/Skill
and desktop negative cases. C03 owns the completed board-create workflow. The legacy shared-realm
loader remains trusted-only, and R02/R03 still own the isolated transport integration.

No live agent was invoked. Tests use synthetic temporary registries and remove their fixtures; no
ordinary package data or credentials are used. Invocation handles are not retained in this receipt.
