## Delivered implementation

`scripts/desktop-profile.mjs` creates an empty profile with a persistent random WebKit store ID.
Its launch mode gives only the child process a clean home, agent directories and temporary directory;
it does not modify the calling shell, copy credentials, or load the user's agent environment.
The native startup validates these directories before constructing Tauri. Native data, logs and
workers use the profile data root. The main window and dynamically created pet share the profile's
WebKit store. The ordinary launch path is unchanged. Updater configuration is removed in test mode.

Baseline profiles refuse real Codex, Claude and pi launches before spawning. This deliberately does
not establish real-agent acceptance; a later agent task must introduce and verify explicitly isolated
test credentials before claiming its real-service gate. Development profiles are **not** a sandbox
for hostile packages, and do not satisfy P02/R02/R03 containment acceptance.

The launcher currently supports macOS 14 or newer. WKWebView owns the physical location of its
persistent store, so that store is identified by the profile UUID rather than being wholly inside the
temporary directory. Removing the temporary directory alone does not remove the WKWebView store.
See the [Tauri data-store contract](https://docs.rs/tauri/2.12.5/tauri/webview/struct.WebviewWindowBuilder.html#method.data_store_identifier).

## Reproduction

Run these commands from the repository. `create` prints the profile directory; use that exact path in
`launch`. Keep each created profile for restart verification. All fixture content is synthetic.

```sh
npm run desktop:build
npm run capability:pack -- tests/fixtures/capability-baseline /tmp/nooki-p00-artifacts
node scripts/desktop-profile.mjs create
node scripts/desktop-profile.mjs launch <printed-profile-directory>
```

Use the app's normal Quit action before restarting that same profile. Confirm the launcher exited
before relaunching. If the shell-launched window is in the background, activate the already-running
application through Finder before interacting; do not repeatedly create ordinary launches. The launcher runs the bundled
build directly, not the installed application. A second `create` returns a distinct native root and
WebKit store. Do not open the test build directly without the launcher: that is an ordinary launch.

In profile A, import `org.nooki.baseline-1.0.0.capability.zip`, review its `storage` and
`documents.publish` permissions, then open **Profile baseline**. Its initial count must be zero.
Publish one synthetic receipt. Quit and relaunch A: both the installed package and count 1 must
remain. Start profile B: it must have no package or receipt; importing the same archive must start
at count 0. Return to A, uninstall the fixture, and verify the synthetic receipt remains in Library.
Reinstall the fixture in A and check the retained private count, then verify B remains independent.
Use the developer center to install the bundled developer Skill in the profile and verify its
destination is the profile's `home/.agents/skills`, without copying ordinary Skills or credentials.

## Native isolation defect and completed acceptance

The original configuration-only assertion was insufficient. Installed Tauri runtime 2.12.2 converts
`WindowConfig` into `WebviewAttributes` without copying `data_store_identifier`, while the builder
setter does carry it. Profile main windows therefore fell back to the default store despite distinct
UUIDs. The repair disables automatic profile-window creation and uses an explicit builder for initial
creation and later main-window recreation. This is why P00 stayed unchecked until real desktop proof.

The original test wrote only the synthetic fixture's namespaced counter/publication; no credentials
were copied. The synthetic fixture counter was removed from the original shared store through its normal
data controls, without clearing unrelated capability data. Native publications remain in the test
profile roots. The default store also persisted ordinary UI navigation choices during that failed run;
no claim of zero default-store writes is made for the original build.

Fresh repair-verification profiles: C `/private/tmp/nooki-profile-oiDe6i`, D
`/private/tmp/nooki-profile-8Mcxia`. The full lifecycle and isolation sequence passed on the repaired build. Native menus sometimes
restored a stalled background navigation animation; the UI tool also reported `noWindowsAvailable`
while the accessibility tree remained readable. Activating the running app through Finder restored
normal interaction, and the complete repaired run used foreground windows. No navigation product fix
was inferred from those automation symptoms. A readable tree or configured UUID alone is not proof.

Repair logs: `/tmp/nooki-p00-webview-red.log`, `/tmp/nooki-p00-webview-rust.log`,
`/tmp/nooki-p00-webview-build.log`; native run logs: `/tmp/nooki-p00-profile-c-restart.log`,
`/tmp/nooki-p00-profile-d-restart.log`, `/tmp/nooki-p00-profile-c-final.log`. The interactive checks
used the real bundled app and archive, native file dialogs, and actual Host publication/storage;
no mocked Tauri bridge was used. Both frontends exited normally after verification.
