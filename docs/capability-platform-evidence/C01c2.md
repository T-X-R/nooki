## Public delivery and trust boundary

`host.board.create(input, {idempotencyKey})` now reaches the native adapter and real task-board
worker from an ordinary installed archive. Canonical types define the input, item reference,
idempotency options and structured error codes. The package import dialog names the `board.create`
permission as draft creation without starting work; its existing source/permission consent applies.
The starter, manifest checker, preview Host, exported contract and Skill are updated together.
Board packages require Nooki 0.4.0 or newer; the checker refuses an older declared minimum. This
version bump is part of the open feature PR, not a published release or merged production claim.

The trusted host controller captures the installation ID/version, not the package's mutation
body. A main-view-only native begin command requires the installed manifest permission and issues
an opaque invocation; release is caller-bound. The create command still derives its caller from
the injected Tauri WebView. Board requests cannot choose owner, operation, grants or generation;
the worker independently validates current authority and permission at the commit boundary.

This controller is explicitly for the legacy shared renderer. Its main-view restriction does not
distinguish two malicious scripts inside that same view, and same-realm code could call internal
commands or tamper with host JavaScript. Installation consent is not an isolated authorization UI.
The approved phase-1 trusted-only boundary remains; R02/R03/K4 must integrate actual isolated views,
restrict controller access, qualify bounded receiving and repeat native identity/containment tests.
No broad desktop/Windows support or hostile-package isolation is inferred from this macOS run.

The client snapshots and validates input before awaiting authority, reserves native-envelope room
with a 63 KiB public limit, and keeps one lazily issued handle per page/job. It shares pending grant
issuance, preserves native error codes and never retries a mutation automatically. A failed grant
can be requested again; an uncertain mutation must reuse its original key/input. The complete
limits and retry semantics are in the [public contract](../../packages/capability-contract/README.md).

## Lifetime and cleanup

Page unmount, job completion and cancellation close the board client and release its handle.
Late grant completion after disposal is released without sending a mutation. A pending worker
effect is still ordered by the native fence; cancellation cannot undo an already committed card.
Successful enable/disable, replacement, rollback and uninstall close existing board clients,
including clients that never requested a handle. Failed registry changes do not prematurely close
the old page. React page scope is created in the effect so development effect replay gets a fresh
Host instead of reusing a disposed one.

Two independent review findings were fixed before desktop acceptance: a rejected release promise
was permanently cached, and an exception from job-finally cleanup could replace a successful result
or the original job error. Failed release now stays retryable while the client stays closed. Retired
clients remain owned in memory and are retried before a later grant for that package or during
lifecycle invalidation. Cleanup failure is reported separately and does not rewrite the job outcome.
Persistent native storage/IPC failure can still prevent release; native capacity limits, generation
invalidation and startup clearing remain the backstop. This is not a claim of guaranteed cleanup
during a dead process or broken disk.
