## Resource policies and owners

P02d1 measures individual archive/store limits. This increment gives independent stores one shared
reservation owner and adds owned event payloads, real asynchronous tasks and native Unix stream
services. This completes P02d's bounded feasibility experiment, not the production resource manager.

| Resource | Per-item / per-owner policy | Shared experimental limit | Production owner |
|---|---|---|---|
| Archive input/expansion | 32 MiB compressed, 16 MiB per entry, 64 MiB expanded, 256 entries | Inspector workload is sequential; R01 must admit/serialize inspections and reserve staging before expansion | R01; P02d1 evidence |
| Private data | 256 KiB value, 16 MiB and 256 keys per store, one writer per store | 64 MiB retained plus staged content, 1,024 files, 16 stores, four writers | R02/R03 native private store, R11 recovery/migration |
| Binary transfer fixture | 64 MiB item, 64 KiB file-write chunk; 128 MiB and four retained items per store | 256 MiB retained plus staged content, 16 files, eight stores, four writers | R07 artifact staging/retention, R11 recovery |
| Queued/delivered notifications | 16 KiB payload, 64 unacknowledged events and 256 KiB per owner | 128 events / 512 KiB across owners, including delivered-but-held payloads | C06 observable runs; R02 transport and unsubscribe |
| Concurrent runs | Two per owner | Four admitted tasks; excess starts rejected with no hidden waiting queue | C06/C07 cancellation and R04 command/job owner |
| Continuing services | One per owner | Two admitted service resources; excess starts rejected | R05 host-owned service registry and stop controls |

These are initial **experiment policies**, not released SDK defaults. The artifact fixture's retained
files model quota accounting, not an eviction policy for Library outputs. Production must preserve
user outputs and report how to free space; a full quota never authorizes silent deletion. Independent
user-owned delegated work has its own host lifetime and must not be stopped as package-owned work.

P02c separately measures admitted IPC operations. These dimensions must compose: a 64 KiB raw file
chunk plus JSON/base64/envelope does not fit a 64 KiB wire-message budget. R02/R07 must select a bounded
binary transport or a smaller encoded chunk and include metadata/encoding overhead. This file-write
experiment makes no claim that the current JSON bridge already transports those chunks.

## Reproduction

From `src-tauri`:

```sh
cargo test --offline --example capability_data_budget_probe
cargo run --offline --example capability_data_budget_probe
```

The executable runs P02d1's real ZIP/file workload followed by this increment's shared-resource
workload. It uses only fresh uniquely named temporary directories, fixed synthetic owner identities,
and native connected Unix stream pairs. No ordinary profile, network destination, real agent or
desktop window is used. The machine-readable output is written only after assertions pass. The
eight-test suite additionally exercises cross-thread admission and injected cleanup failures.

## Native observations

**Disk reservations.** Four private stores fill the shared 64 MiB budget with actual files. A fifth
cannot add one byte. Removing a 256 KiB value admits the fifth store's replacement, whose bytes are
read back independently. Dropping the store objects leaves the files charged: object lifetime must
not stand in for file deletion. A separate workload fills 1,024 empty files and 16 directories, then
rejects the next file/store, so zero-byte objects cannot bypass count limits.

Four 64 MiB transfer files fill the shared 256 MiB content budget. An extra byte is refused. After
one file is removed, a new 64 MiB declaration reserves the entire amount **before** its first 64 KiB
write. Dropping that unfinished transfer removes staging and releases its full reservation; a new
64 MiB transfer then commits with exact readback. The workload independently fills the 16-file and
eight-store limits. Four simultaneous staging handles fit; a fifth fails, and dropping them returns
the writer count to zero.

Two actual writer threads compete for a shared 24 MiB test pool while each requests/writes 16 MiB.
Exactly one is admitted and holds a real 16 MiB staging file; the occupied snapshot is 16 MiB, and
both threads finish with zero bytes/files charged. A separate fault injection moves a written byte
to an orphan path and places a directory at the staging path, causing real unlink failure. The byte,
file and writer reservation remain charged; another file is refused. This conservative leak requires
reconciliation instead of pretending cleanup succeeded. R11 must implement recovery; no recovery
ledger is added to the production app by this probe.

**Events.** A and B each hold sixteen 16 KiB payloads, reaching 512 KiB. Further owner/global writes
fail without changing existing data. Popping an event leaves its bytes charged until the owning
`Event` is dropped; only then can C add an event. Discarding A's queued events preserves B's complete
FIFO byte sequence and C's payload. A separate 128-empty-event load reaches the count limit. Dropping
the queue releases everything. A two-thread/two-queue test sharing a one-event pool admits exactly
one real payload. The normal measured policy remains 64 events per owner / 128 globally.

Overflow rejects the newest enqueue; there is no silent overwrite or automatic retry queue. This
models bounded notifications, not an authoritative history store. C06/R02 must expose current state
or resynchronization after overflow and keep host stop/disable management outside a saturated package
notification queue. An event already delivered to a consumer remains charged until that consumer
releases it; removing queued entries alone does not acknowledge delivered data.

**Runs.** Four admitted Tokio tasks each own and hash an actual 64 KiB payload, report the expected
SHA-256 result, and remain suspended with their payload and capacity lease. A's third run and C's
fifth global run are refused. Aborting and awaiting one task permits C's replacement; aborting and
awaiting all remaining tasks leaves the pool empty. This is evidence for async task ownership,
not real-agent cancellation, noncooperative native code termination or package-generation revocation.

**Services.** Two admitted tasks own real native Unix streams and exchange startup bytes. Additional
owner/global starts fail. Stopping A aborts and awaits its task; its peer reads EOF. B then successfully
echoes `still alive`, demonstrating that the other service remains operational. C takes the released
slot. Stopping B/C produces two more observed EOFs. Event/run/service pools all end at zero counts,
zero payload bytes and empty owner maps. This is native handle-lifetime evidence, not a media backend
or proof of page-independent music playback; R05 must retain P02b2b2a's desktop media evidence in its
actual implementation.

## Limits and acceptance boundary

- Shared disk reservations are atomic within one process. Stores are fresh and single-writer; the
  pool persists charges when handles disappear, but does not reconstruct them after a crash/restart.
  Store-directory slots remain charged while their directories are retained. No reopen API, durable
  registry, idempotent commit or repair workflow is implemented here. P02d1's other limits still apply.
- Disk figures count declared/retained logical content and objects, not filesystem allocation blocks,
  metadata, free-volume capacity or process RSS. Cleanup failure intentionally exhausts capacity until
  a future reconciler proves which content is gone. Counters never authorize deletion of user output.
- Live owner IDs are a fixed synthetic allowlist, not authenticated package identities. R02 must bind
  owners/generations at the native boundary. All payloads in this fixture are already trusted native
  values; this does not resolve P02c's pre-dispatch deserialization/allocation boundary.
- Async abort is awaited before claiming task/handle release. A Rust future doing non-yielding native
  computation could prevent that cleanup; this fixture's hash is finite and its services await I/O.
  Webview forced-stop evidence remains P02b2b2a, and provider/process stop policies remain C07/R05.
- Resource counts do not establish total CPU/RSS bounds or fairness. There is no desktop fault-load
  claim from this CLI test and no Windows/Linux support claim. P02e must audit the full runtime path
  and unresolved allocation/compatibility constraints before K0.
