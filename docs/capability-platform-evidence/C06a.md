## Why the existing chat path is insufficient

Current `ConversationHost::run` routes through the existing Codex/native adapters. Ordinary Codex
chat resumes with workspace writes and may install the Nooki capability dynamic tool. Its request
handler declines unsupported approvals; it is not a general Host-owned package-run approval surface.
The board path has a stricter configuration, but neither path is a ready-made public Agent run API.
C06 will reuse transport and native run identity while explicitly binding a dedicated effect scope.
It will not add a model client, credential store or substitute scheduler.

C06 has been split in the existing checklist into policy feasibility, durable scoped intent,
adapter dispatch/reconciliation, public SDK/Host interaction and independent/real-agent acceptance.
C06 depends on completed C01/C02 and may progress independently of C05c; both remain required for K2.

## Reproducible native probe

```sh
node scripts/probe-capability-agent-policy.mjs /absolute/path/to/codex
```

The probe creates a fresh profile through the existing launcher and uses only new synthetic files.
It passes a child-only environment with an empty Codex home; no credentials are copied or read.
An unsandboxed positive control reads the synthetic foreign file and contacts a localhost fixture
server, proving those resources exist before testing refusal. The native `codex sandbox` then:

- reads approved input and writes its designated output;
- denies the sibling synthetic private file and a symlink to it;
- denies writes to inputs, unrelated files and an output symlink leading outside the output root;
- cannot contact the reachable localhost endpoint; its request counter remains zero.

The script then starts an ephemeral app-server thread with the same named profile, no selected
capability roots/dynamic tools and no turn. It asserts the profile ID, `approvalPolicy: never`,
exact output-only writable roots, disabled network and excluded implicit temporary write roots.
The process is terminated after acknowledgement. **Zero model turns were sent.**

Initial checkpoint profile: `/private/tmp/nooki-profile-WtWdvw`. The audited final run below supersedes
its policy and network-check scope.
Receipt: `policy-probe.json` within that root; sandbox stderr is retained alongside it.
Final log: `/tmp/nooki-c06-policy-probe-final.log`. `node --check` and `git diff --check` pass.

## Failed controls and limits

The initial profile using only `:minimal`, explicit input reads and output writes unexpectedly read
an unrelated synthetic file under `/private/tmp`. Adding a root deny did not prevent that read.
A nonexistent profile was correctly rejected, and an explicit deny for the synthetic foreign path
was enforced; the selected configuration was not simply ignored. Replacing `:minimal` with a small
handwritten runtime-root list caused the sandboxed shell to exit 134, so that candidate was rejected.

The passing probe retains `:minimal` but explicitly denies `/private`, `/Users` and `/Volumes`, with
more-specific grants for input/output directories. This establishes the tested mechanism on macOS
15.6.1 / CLI 0.170.0. It is **not** an exhaustive inventory of every runtime read root or a production
allow-list audit. The source audit and revised controls below establish the version-pinned feasibility boundary. C06c must additionally validate configuration/connector/tool restrictions,
Host-only approvals/questions, durable reconciliation and cancellation. Neither acknowledgement
nor a successful shell probe proves those later requirements.

## Completed source audit and revised controls

The official `rust-v0.170.0` source resolves to commit
`29eb79e9866b3262a777fdf8195c1b9e63684c91`. The following source paths explain the observed behavior:

- [Scratch policy](https://github.com/openai/codex/blob/29eb79e9866b3262a777fdf8195c1b9e63684c91/codex-rs/sandboxing/src/seatbelt_scratch.rs)
  adds process scratch reads/writes for `/private/tmp` and `/private/var/tmp` when platform defaults
  are requested. Explicit non-root restrictions are lowered into these grants.
- [Permission projection](https://github.com/openai/codex/blob/29eb79e9866b3262a777fdf8195c1b9e63684c91/codex-rs/protocol/src/permissions.rs)
  treats a root deny as the default rather than an unreadable-root exclusion; this explains why
  adding `/` did not remove the implicit scratch read.
- [Seatbelt assembly](https://github.com/openai/codex/blob/29eb79e9866b3262a777fdf8195c1b9e63684c91/codex-rs/sandboxing/src/seatbelt.rs)
  appends platform defaults and `/Applications` reads separately. Literal path exclusions do not
  remove all those fixed defaults. Deny globs are emitted after the allowances and also constrain
  writes/ancestor renames.
- [Platform defaults](https://github.com/openai/codex/blob/29eb79e9866b3262a777fdf8195c1b9e63684c91/codex-rs/sandboxing/src/seatbelt_read_only_platform_defaults.sbpl)
  enumerate the runtime paths, device access and system IPC; this is broader than package-selected
  source data and must be included explicitly in the effect-policy review.

The final probe retains native platform support, denies scratch/private/user/volume access except
its explicit input/output grants, and adds final deny globs for `/Applications`,
`/Library/Preferences`, `/Library/Filesystems/NetFSPlugins`, `/opt/homebrew/lib`, `/usr/local/lib`,
`/private/etc` and `/private/var/db`. Patterns cover the directory and its descendants. A synthetic
sealed subtree proves directory-content and descendant refusal; a denied filename pattern proves
that both existing files and newly created matching files are protected despite a writable parent.

Remaining readable runtime resources include system executables/libraries/resources under
`/bin`, `/sbin`, `/usr/{bin,sbin,lib,libexec,share}`, system framework roots and `/Library/Apple`.
Native terminal/device, metadata traversal, system-service and logging allowances remain. The profile
is an OS execution boundary, not a guarantee that file existence/owner metadata is secret: `ls -ld`
can reveal metadata for the sealed synthetic directory while listing its contents and reading its
file are denied. No package may infer document-read or external-effect authority from such metadata.

The strengthened profile initially made curl fail while reading OpenSSL configuration, before a
connection attempt. That failed candidate is not network-denial evidence. The final probe uses the
same Bash direct-TCP operation outside and inside the sandbox. Its positive control reaches the
local server; its sandboxed control exits with a socket/connect permission error and the server
receives no request. This rules out the curl-startup false positive.
