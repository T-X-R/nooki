## Workload and observed sequence

A alternates 128 KiB IPC bodies and small resource GETs in batches of eight, waits 100 ms between
batches, and stops at 4,096 attempts or 60 seconds. A deadline aborts outstanding fetches. B makes a
valid small echo call every 250 ms and periodically reports successful results. Hidden-page timer
throttling is part of the native run; the nominal intervals are not claimed as achieved throughput.
The shell retains separate management authority and can destroy A at any time.

The diagnostic collector already caps at 256 events. Rejection sampling now retains the first 16
refusals and then every 64th, with an atomic total counter exposed to native status. This preserves
control/peer evidence instead of exhausting the cap with repeated errors. It is not a production
logging system. P02e2's earlier wording suggesting an unbounded event vector is corrected separately.

| Observation | Native elapsed time | Result |
|---|---:|---|
| Sender starts | 21,442 ms | Explicit count/concurrency/duration bounds recorded |
| Status during pressure | 32,359 ms | 740 refusals; shell answers, A still present |
| Peer result before removal | 35,459 ms | 24 attempts / 24 exact successes |
| Shell destroys A | 36,155 ms | 992 refusals; A absent from returned native view list |
| Status after removal | 53,319 ms | Still 992 refusals; receive bytes/count both zero; B and shell alive |
| Last peer result before quit | 58,506 ms | 100 attempts / 100 exact successes |

Removal occurs 14,713 ms after the sender starts, before its self-imposed deadline or request cap;
there is no sender-completed event. Refusal samples immediately preceding removal establish active
pressure. A's heartbeat freezes at 110; B advances to 81 and the shell to 179 at the final status.
The native action records less than 1 ms for dispatching removal; this is not an end-to-end UI latency
benchmark. The UI actually removes A and shows B's successful-call counter. Normal quit exits 0.

The receive peak in this mostly synchronous refusal case is one request / 65,536 reserved bytes.
P02e2 remains the separate evidence for four simultaneous requests / 256 KiB peak. Neither number
is total WebKit/native memory. This run does not simulate arbitrary maximum-rate flooding or OOM;
it supplies the missing finite stop-under-arrival-pressure case for P02 feasibility.

## Reproduction and checks

Build the `capability_runtime_probe` example with `--features runtime-probe-receive`, launch the
bundle using a fresh isolated profile, select the embedded workspace and click **Run finite receive
pressure** once. Leave A visible, request native status while refusal counts grow, then click
**Destroy A** before 60 seconds. Show B, request status again and quit normally. Do not infer stop
under load from a run where the sender already ended.

Independent assertions over the retained trace verify increasing refusals before removal, stable
refusals afterward, removal before the deadline, no normal sender-completion event, successful peer
calls before and after removal, released reservations and fewer than 256 retained events. The
receive-mode suite passes all 11 tests; default-mode compatibility passes all 9 tests. JavaScript
syntax and diff checks pass. Logs: `/tmp/nooki-pressure-tests.log`,
`/tmp/nooki-pressure-default-tests.log`, `/tmp/nooki-pressure-build.log`.

This completes the bounded extra case, not the production runtime. P02e3b records the combined
decision, support policy and encoded budgets.

Default desktop build passes (30.94-second native release build, 24.14 MiB bundle), with the existing
large-chunk advisory. Local reinstall and `codesign --verify --deep --strict /Applications/Nooki.app`
pass. Logs: `/tmp/nooki-pressure-app-build.log`, `/tmp/nooki-pressure-app-install.log`.
