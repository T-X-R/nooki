## Boundary and ownership

The independent task-board worker cannot rely on a check completed before its IPC request was
queued. A caller timeout does not cancel a queued request. The effect-boundary validator therefore
shares a stable `capability-authority.lock` file with grant issuance, direct revocation, installation
registry commits and host startup. The lock is never unlinked during use. Each acquisition uses
nonblocking native flock with a bounded five-second retry window; exhaustion returns `RESOURCE_BUSY`
without acknowledging a mutation. The short synchronous callback holds the fence through its effect.
It must not await IPC, re-enter authority or acquire an inconsistent lock order.

`with_worker_board_authority` reads current live authority and the installation registry under that
fence. It checks the native caller, fixed `board.create` / `board` scope, installed version, enabled
state and generation before invoking the callback. `PlatformState::with_board_authority` uses the
same path, so local effects cannot bypass worker ordering. Registry mutations hold their local
registry write lock before the shared fence; worker validation and direct revocation do not acquire
the local registry lock. No authority lock is held while sending or awaiting a worker request.

The live coordination record is `capability-invocations.json` at the native data root, outside the
user-data backup roots. It stores SHA-256 digests of the random handles, with native caller and
package/version/generation context. The raw bearer handle is never persisted by this mechanism;
passing a stored digest as a handle fails. The record uses mode 0600 on Unix and atomic replacement.
There is no in-memory authority cache to flush back over a newer process's state.

Host startup obtains the same fence and replaces the record with an empty one. An already admitted
effect completes first; subsequent checks reject the old handle. Restart never restores previous
live grants. Reset failure aborts loading rather than quietly retaining previous-process authority.
The file is process coordination, not a recoverable session store. An unexpected host crash does
not itself clear the file; this increment implements startup invalidation, not a host-liveness lease.
Runtime destruction and public invocation delivery remain integration obligations.

## Bounds and failure semantics

- Existing authority limits remain 16 per package and 256 total. Context ID/version strings are
  limited to 256 bytes each at issuance; native caller remains ASCII and at most 128 bytes.
- Reads consume at most 512 KiB plus one overflow byte; oversize, corrupt or over-count records
  fail closed. Serialized writes also enforce the 512 KiB ceiling.
- Grant/revoke/reset write and sync a staging file, rename, then sync the directory. Pre-rename
  failure leaves the prior record effective and returns an error. Post-rename directory-sync failure
  returns `OUTCOME_UNKNOWN`; there is no false restoration of the prior visible authorization.
- Lifecycle invalidation is authoritative in the installation registry. It does not depend on
  rewriting the live record. Stale entries are pruned on the next successful issuance, reclaiming
  capacity. A blocked live-record staging path cannot make a disabled/replaced generation valid.
- Registry commits compare the current on-disk registry with the host snapshot under the fence.
  A stale host reports `CONFLICT` instead of overwriting newer installation state or issuing from
  it. The caller must reload; this does not claim multi-instance package-directory transaction support.
- New worker authority requires the existing Unix lock support. Conditional fencing/reset preserves
  the legacy non-Unix registry/load path. Only macOS was executed; no new Windows/Linux qualification.

## Verification

Before implementation, five new non-child scenarios failed against an explicit unimplemented
validator and the memory-only authority implementation; the child-entry harness returned normally.
Log: `/tmp/nooki-c01b1-red.log`. The final new test binary has six behavioral tests plus the child
entry used by its process test:

1. Worker validation without constructing another host: correct context; wrong caller, handle,
   operation and resource denied; revoked handle rejected.
2. Digest-only record and mode 0600; digest cannot be replayed; restart clears old handles; a prior
   host cannot revive them by issuing again; revocation by one host is visible to another.
3. Disable/re-enable changes registry generation even when grant-file staging cannot write;
   old entries fail worker checks and subsequent issuance reclaims their capacity.
4. Grant/revoke/startup-reset write failure preserves exact prior bytes and never reports success;
   corrupt and 512 KiB + 1 records reject calls; successful startup clears them without restoring
   old handles.
5. A stale host cannot issue from or overwrite a newer disabled registry.
6. Actual separately spawned native processes hold the effect fence while another host thread
   attempts direct revoke or disable. Neither returns success before effect release. In both cases
   a second process given the queued old handle fails before entering/writing its synthetic effect.

The process test invokes the production validator from a test executable. Its synthetic file effect
is not an actual task-board create operation or a worker-RPC timeout test; those remain C01b2.
Child output is suppressed and process results/effect files are asserted by the parent. No live
agent, ordinary profile or real user data is used. No raw handle is included in this receipt.

Independent adversarial review of the changed authority/registry paths found no substantive issues
under this scoped contract. Subsequent edits added failure/oversize assertions only. The
post-rename directory-sync uncertainty and five-second busy deadline are source-reviewed; no
fault-injected directory-sync failure or held-lock deadline experiment is claimed.
