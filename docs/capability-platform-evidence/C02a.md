## Behavior and ownership

Selected snapshots now carry a private installation-generation binding as well as package ID and
version. Reads/listing reload the native registry, require `documents.read-selected` and check that
binding. A valid snapshot survives host restart, but disable/re-enable, update, rollback or reinstall
cannot revive old package access. Older records without a generation require a fresh user selection;
their content remains accessible through the host's user-citation path. No generation is returned
as public grant metadata, and no public API types or version numbers change in this native slice.

Explicit host-side revocation persists a marker in `document-grant-revocations`, outside user-data
backup/restore roots. Marker presence denies future package reads, including malformed markers;
revocation neither deletes the snapshot nor erases content already delivered. Repeating revoke
confirms durability even if a later restore removed the underlying snapshot. Invalid or previously
unknown IDs without a marker still fail. This slice exposes no new renderer/package revoke command.

Snapshot creation reads at most the existing 50 selected documents / 8,000,000 content bytes,
publishes exclusively, and syncs file content and directories before acknowledgement. Repeating the
same ID and document set returns the original bytes, without recapturing later source edits. Another
selection conflicts. An unpublished staging file left by interruption can be removed safely while
holding the writer locks. A visible snapshot whose durability cannot be confirmed returns
`OUTCOME_UNKNOWN`; retry must sync the existing file and directories before success.

The native order is `task-data.lock` → authority fence → process-local `DATA_LOCK`. It matches the
board worker's data-before-authority order and coordinates with user-data restore across processes.
The authority fence spans the current-registry decision through synchronous capture/read/revoke;
the Library lock covers the entire operation, not individual document reads. A busy data transaction
returns `RESOURCE_BUSY` before the operation. Host citation reads also respect data replacement.

Before restore/recovery replaces a changed or removed grant, it durably revokes that ID. Therefore
restoring a backup predating a grant cannot recycle its ID for new content. Byte-identical snapshots
retain their existing authority, subject to generation and explicit revocation. A prepared,
uncommitted restore blocks document operations until recovery, including when another process
outlives the restore owner. Reusing the currently committed restore transaction ID is rejected before
starting another replacement, so an older commit marker cannot certify a new interrupted attempt.

Revocation decisions are local authority, not portable user artifacts. Restoring snapshots into a
different installation requires reselection because its generation differs. Revocations completed
before a restore failure remain in force; the user may need to select again. Explicitly restoring a
backup that omits a snapshot can remove that user-data snapshot, but cannot make its old ID reusable.
This change does not redefine general backup durability or claim a complete power-loss audit.

## Reproduced failures and review

The original generation tests reproduced old access returning after re-enable and same-version
reinstall. Additional falsifying tests reproduced stale `.pending` files preventing retry, reads
escaping an in-progress restore, revoke failing after restore removed its snapshot, reuse of a grant
ID after older-data restoration, recapture during an interrupted restore, and repeated restore IDs
starting another replacement. Each now has a passing regression.

Three bounded independent review cycles covered only authorization, restore ordering and durability.
Six actionable findings were addressed: missing cross-process restore coordination, removed-ID
reuse, missing file sync on replay, non-idempotent revoke after snapshot removal, the interrupted
restore window, and ambiguity from reused restore transaction IDs. The final transaction-ID fix was
verified by its failing-then-passing test and the full regression; no fourth review was performed.

One full regression run returned the explicitly retryable pre-effect data-lock busy response in the
legacy-grant listing test. The test now retries only that exact admission error, for a bounded
interval, and still requires a real empty authorized listing. Permission errors, recovery-required
errors and unknown outcomes are not retried or converted to success. The final complete run passes.
The failure is retained in `/tmp/nooki-c02a-native-final.log`; its precise transient lock owner was
not established, so no specific process-inheritance root cause is claimed.

## Remaining acceptance

C02b must implement the host-owned picker, recipient/purpose display, explicit dismissal, pending
approval binding to the shown installation, caller disposal, public read/revoke flow and exported-kit
desktop verification. This native slice does not clear those requirements or claim V-UI/V-N picker
acceptance. Legacy shared-realm packages remain trusted-only; browser development fallback behavior
is not upgraded into an isolation boundary. Board source integration remains C02/C03 work.
