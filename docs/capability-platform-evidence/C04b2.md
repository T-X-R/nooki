## Authorization and atomic effect

The native controller issues an operation-specific `board.attachDelivery` invocation. An invocation
for `board.create` cannot attach, and an attachment invocation cannot create or execute a task.
The effect separately requires the installation-bound, attach-only task grant from C04b1 and the
exact approved item revision. Current registry authority, task grant, revision checking and the
delivery commit share the task-data and authority fences. The main-window controller identity comes
from the native caller, never a request-body field. The renderer worker gateway rejects the private
attachment operation. No Tauri command or public package interface is exported in this increment.

Each request has a bounded key, title, task reference and 1–50 distinct document references. A plain
reference requires current publication permission and ownership of the document namespace; an
optional expected revision is the canonical SHA-256 revision returned by publication. A selected
reference requires the exact active document grant, title and captured revision, retaining the
approved snapshot rather than a later original. Cross-package plain references and forged selected
references fail before a board effect.

The effect appends to `attachedDeliveries`, preserving the existing Agent `delivery`, task status,
description, execution authority and all unrelated cards. Each delivery records native provenance,
time, canonical document references and retained text. Keeping text inside the board, as existing
Agent delivery data already does, lets one atomic board save commit the content, affected revision
and idempotency receipt together. There is no separately committed snapshot to orphan on failure.

Retained deliveries are capped at 64 per card, 256 across the board and 8 MB serialized content.
Incremental capture also enforces the byte limit. Receipts are capped at 1,024 total, 256 per package
and 1 MiB. Capacity errors retain earlier deliveries and receipts. The native board validator checks
both structures during load/restore; legacy renderer saves preserve native attachments and receipts
and cannot forge them. Attachment writes rotate the board write token to reject stale whole-board
saves. Explicit user task deletion may remove its delivery, while its original receipt remains.

## Replay, lifecycle and document consistency

Receipts bind package, operation and idempotency key to the normalized input and original result.
Exact committed retries first require a currently valid native invocation, then return metadata from
the receipt without reading the source again, adding another delivery, or reauthorizing a new effect.
Changed input under the same key conflicts. A revoked selection blocks new effects but does not erase
an already committed result. Removal or obsolete installation authority blocks the invocation itself.
A fresh valid invocation after restart can recover the original result, including after a lost reply.

The retained text survives source editing/deletion, grant revocation and package removal. Restore
explicitly restores the archived board/receipts and C04b1's external epoch invalidates old task grants.
An interrupted restore blocks both new effects and receipt replay until recovery.

Publication and the task worker run in different processes. A new library file fence therefore
serializes cooperating publication/edit/delete/restore paths with capture through board save; the
existing process-local mutex alone was insufficient. Lock order is task-data, authority, library file
fence, then the library mutex where needed. Library-only paths use the applicable suffix. Unix lock
admission waits at most five seconds, then reports `RESOURCE_BUSY`; non-Unix retains the previous
library mutex behavior and does not gain native worker support from this change.

## Verification

The original five effect tests failed before the attachment operation existed. Sixteen focused native
tests now cover preservation, current revisions, cross-package/operation/caller denial, malformed
input, canonical document revisions, source revocation, retained content, lifecycle, restore,
capacity, precommit failure, post-rename uncertainty, concurrent calls, first-reply loss, restart and
revocation while a request is queued. The publication helper is one no-op parent-suite entry and is
also launched in three real child processes for publish/edit/delete races.

A FIFO pauses the real worker inside board save after source capture. A second process must remain
blocked while attempting publication, editing or deletion. Removing the publication fence made the
test fail with `publish escaped while the attachment was inside its board save`; restoring the fence
passes all three cases. The FIFO is unlinked before draining so this injected save cannot rename a
FIFO over the board. Retry captures the subsequently published/edited text; deletion rejects retry.

Bounded independent review found the missing cross-process fence and a timestamp comparison where
the canonical publication hash was required. Both were fixed with failing-then-passing coverage.
The second bounded pass found no concrete remaining issue in fence coverage, ordering or revision
identity. Full regression initially stopped during an old document-selection fixture's duplicate
installation setup; the isolated rerun reproduced it. Adding an atomic sequence to timestamp-based
fixture paths and requiring a newly created directory removes parallel path reuse. The new attachment
fixtures use the same uniqueness rule and short paths for macOS Unix sockets.

Final `cargo test --manifest-path src-tauri/Cargo.toml` passes **237 top-level tests plus one nested
profile child**, with two existing live-agent tests ignored. `npm test` passes **175 platform + 5
capability tests**. Logs: `/tmp/nooki-c04b2-native-verified.log`, `/tmp/nooki-c04b2-js.log`;
negative controls: `/tmp/nooki-c04b2-revision-red.log`, `/tmp/nooki-c04b2-race-red.log`.

The same attachment suite passes with `NOOKI_ATTACHMENT_TEST_BINARY` set to
`/Applications/Nooki.app/Contents/MacOS/app`. Three tests launch actual installed workers: concurrent

The remaining tests still call the Rust library directly and are not relabeled installed-app tests.
