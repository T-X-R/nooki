## Purpose and initial policies

The legacy installer accepts only two or three UTF-8 files, up to 12 MiB compressed and 10 MiB per
entry. Its bounds cannot establish budgets for a future package with binary assets. Current browser
private storage has no explicit product quota. This experiment measures candidate limits with real
ZIP reads and temporary disk files before the new production format and storage services exist.

| Resource | Experimental limit | Evidence | Production owner |
|---|---|---|---|
| ZIP input | 32 MiB compressed | Valid ZIP at exactly the limit is read; one byte over is refused before parsing | R01 inspector/format and packer |
| ZIP expansion | 16 MiB per entry, 64 MiB total, 256 entries | Exact limits pass; each plus-one case fails; aggregate check also counts actual decompressed bytes | R01 inspector/asset staging |
| Private byte store | 256 KiB per value, 16 MiB per store, 256 values | Full store, value/count overflow, removal and replacement/readback | R02/R03 authoritative private storage; R11 migration accounting |
| Binary item | 64 MiB per item, 64 KiB per write | Full-size file written and independently read byte-for-byte; item/chunk overflow refused | R07 artifact transfer and R02 transport |
| Transfer fixture store | 128 MiB retained plus staged content, four committed items, one writer | Two 64 MiB files fill it; removal restores capacity; fifth item refused even when empty | R07 staging/retention; P02d2 aggregate reservations |

Values are provisional resource policies, not public API constants or production guarantees. The
private value limit exceeds an IPC message, so a future implementation must chunk it or deliberately
choose a smaller public value limit; it must not send a 256 KiB JSON body through P02c's 64 KiB guard.
The 64 MiB fixture is synthetic binary data, not a claim about all presentation/audio sizes. Real
PPTX and codec usability remain R13–R15 acceptance and may require an explicit revised quota.

## Reproduction and measurements

Run from `src-tauri`:

```sh
cargo test --offline --example capability_data_budget_probe
cargo run --offline --example capability_data_budget_probe
```

The executable owns a fresh uniquely named `nooki-data-budget-*` temporary directory and removes
only that directory on ordinary completion. It prints measurements only after its byte/content and
failure assertions pass. It imports no production application library, starts no browser or agent,
and does not read ordinary Nooki data. This is native file/data evidence, not a desktop UI test.

The retained run completed in **4,206 ms**; duration is descriptive, not a latency guarantee.

- A **65,662-byte** compressed ZIP expands to exactly **67,108,864 bytes**, read through a 64 KiB
  buffer. An extra expanded byte fails. Entries of 16 MiB pass; 16 MiB + 1 fails. A separately
  generated stored ZIP is exactly 32 MiB and passes. An input length of 32 MiB + 1 is refused.
  Exactly 256 empty entries pass and 257 fail. Compression ratio alone is not used as a rejection
  rule: legitimate compressible data fits if its actual size fits.
- The private store contains 64 distinct 256 KiB values, totaling 16 MiB. A new byte is refused.
  Removing one value permits a new full-sized value. Both oversized and capacity-denied replacement
  preserve the old bytes. After freeing another slot's bytes, same-key replacement succeeds and
  its complete content is read back. A separate fixture fills 256 empty keys to test count independently.
- The transfer store writes a 64 MiB file in 1,024 chunks and independently reads every byte back.
  A 64 MiB + 1 declaration fails before creating staging. An incomplete commit and an ordinary
  dropped transfer remove their partially written file and leave no published result. Oversized
  chunks poison the transfer; later writes/commit cannot turn that failed transfer into success.
- Two 64 MiB files reach the store's 128 MiB limit. Another byte is refused. Removing one allows an
  8 MiB recovery file whose bytes are independently verified. A **960,044-byte, 60-second PCM WAV**
  matching the desktop probe's sample shape is transferred in chunks and compared byte-for-byte;
  playback is not retested by this program. A fourth empty item fits, and a fifth does not. Final
  usage is four items / **76,457,516 content bytes**, before fixture teardown.

The store counts the old value while staging its replacement. Otherwise a net-size-only check
would permit temporary content above the limit. Consequently replacing at full capacity requires
freeing space first; the error states that action. Accounting covers logical file content, not
filesystem block rounding, metadata, journal bytes, free-volume reservations or process RSS.

## Failure checks and implementation boundary

Three native tests pass. In addition to the executable's boundary workload, they verify:

- Traversal/absolute/noncanonical paths fail without extracting; corrupt stored-entry content fails
  CRC validation when actually read. The prototype also rejects duplicate paths, directories and
  symlinks, but this receipt does not substitute for R01's complete malformed-archive matrix.
- Writing beyond the declared size makes subsequent writes/commit fail and leaves old content intact.
- A real rename failure (a directory at the intended synthetic destination) publishes no file,
  removes staging, leaves accounting unchanged and permits a subsequent successful write.
- Invalid private keys cannot address parent/absolute paths or the internal staging filename.

The archive reader inspects bytes but does not validate the new manifest or activate/extract code.
It checks central-directory declared sizes and actual streamed sizes; ZIP parser allocations occur
before the entry-count check and are not measured as a hard allocation bound. The pinned ZIP reader
performs CRC validation. No decompression time bound or sustained hostile-input benchmark is claimed.

The store deliberately models **one fresh single-writer directory**, using a Rust mutable borrow
to exclude simultaneous writers. It has no external IPC, authority/grant checking, reopen/restart
ledger, idempotent commit token, concurrent transfer handles, fsync of the containing directory, or
crash recovery. Drop cleanup is best effort on filesystem errors; the tests observe successful
cleanup on this machine, not guaranteed cleanup after abrupt process death or an unwritable volume.
Retained artifacts are not subject to automatic eviction in this experiment.

P02d2 must measure profile-wide reservations across stores, queues, concurrent runs and live service
handles. A bound on one store does not bound arbitrarily many package stores. R07/R11 must implement
the transactional recovery and production retained-output semantics. P02d and K0 remain pending.
