## Behavior

`capability_agent_runs.rs` retains the installation generation/version, restore scope, request key,
instructions, exact selected-source text, chosen agent, complete policy digest, optional output
schema, native approval receipt and run identity in one bounded journal. Native controllers must
authorize every operation, including replay, inside the existing data/authority fences. The journal
checks reference/snapshot correspondence; it does not replace native grant validation or certify
that a requested agent, policy or output schema is supported.

An identical request returns the same run and retained inputs without recapture. Changed intent
under the same scope/key conflicts. A durable `Approved` -> `Pending` transition records a stable
client-message identity before an adapter may be contacted. Only the first successful claim grants
submission eligibility. A pending retry reports `OUTCOME_UNKNOWN`; observation preserves the same
identity. Even a crash before the adapter call requires reconciliation rather than automatic replay.
This is a local journal guarantee, not remote exactly-once execution.

The journal retains at most 256 runs, 8 MB of input text and 12 MB of encoded data. Instruction,
source-count and schema limits are checked before persistence. Full storage refuses new work and
preserves existing receipts. Writes sync a temporary file, rename it and confirm file/directory
durability; an uncertain durability acknowledgement cannot grant dispatch eligibility.

Backup includes and validates the journal. Restore staging always marks imported records as history
without execution authority, preserving any submission identity. Scope checks additionally reject
old installations and restore batches. This explicit import marker is necessary: a modified archive
could otherwise predict the restore transaction ID and present a matching scope. Recovery of an
interrupted restore remains under the existing data transaction; imported history never starts work.
