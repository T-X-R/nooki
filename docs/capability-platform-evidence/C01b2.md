## Delivered transaction

The worker's private `capability-create` operation now creates an ordinary `todo` card and its
idempotency receipt in the same `task-board.json` replacement. The card has a native random identity,
revision 1, title/description, empty sources and native package/version provenance. It has no Goal
engine, execution authorization, thread, run or queue position. Worker reconciliation does not start
an agent for it. The existing explicit delegation workflow remains separate.

The worker holds its task-data lock, then obtains the [C01b1 authority fence](C01b1.md). The current
native caller, fixed operation/resource scope and active installation generation are checked inside
the worker, before receipt lookup or any effect. Both locks remain held through persistence or replay
confirmation. No IPC or agent await occurs inside the authority callback. A queued request whose
handle was revoked before it reaches this boundary cannot write, even if its client already stopped
waiting for a response.

The receipt key hashes the canonical tuple `(native package ID, board.create, idempotency key)`.
The payload hash uses the typed title/description/sources input, with absent description normalized
to an empty string and absent sources to an empty list. Field order does not affect it; changed
content does. Whitespace in accepted text is preserved. The ledger retains the original item
reference/revision and payload hash, not the bearer handle or caller-provided owner/scope. Same
key/input returns the original reference; changed input reports `CONFLICT`. Installation generation
is an authority check, not part of the durable key, so a newly authorized invocation after restart
can recover the original result. Deleted items are not recreated by receipt replay.

Input is a strict private envelope; unknown fields are rejected. Nonempty source references return
`UNSUPPORTED_SERVICE` until C02/C03 connect authorized snapshots. They are never silently discarded
or resolved as arbitrary document IDs. No new public capability permission or SDK method is exposed
in this increment. Native trusted callers use the private worker operation; the generic renderer
entrypoint now accepts only the established board-control allowlist and rejects this operation and
worker-management commands.

## Persistence and existing board compatibility

The existing task-board writer syncs the staged file, renames it, then syncs its directory. A failure
before rename leaves neither the new item nor its receipt committed. Failure after rename reports
`OUTCOME_UNKNOWN`. Receipt replay reattempts the directory sync before acknowledging success: a
visible record alone is insufficient when the previous durability confirmation failed. Neither
unknown outcome nor retry generates a second item.

Once native creation has occurred, the board carries an opaque `writeToken`. A legacy whole-board
save must present the current token; successful native creation and legacy saves replace it. A
stale renderer snapshot therefore cannot erase a new native item or overwrite another accepted
draft save. Existing Goal rows remain preserved by their previous native-owner merge behavior.
The current frontend preserves root fields through its object spreads and replaces local state
with the native saved result; a conflict requires refresh before another save.

The native ledger is retained independently of cards. Renderer-provided receipt data is ignored;
only the authoritative ledger is preserved. Matching native cards retain their package provenance;
accepted user edits increment their item revision. Caller-provided revision/provenance cannot
replace those values. The original create receipt remains immutable even when the user edits or
deletes its card. This does not implement the later public update/selection/delegation grants.

Backup capture includes the ledger with its board file, and backup validation checks the new fields.
Deliberately restoring an older backup is still a user-requested rollback of board state; this slice
does not add a separate non-rollback receipt journal or restore-time invocation invalidation. R11
must reconcile recovery semantics before general production lifecycle acceptance.

## Initial bounded policy

| Boundary | Policy |
|---|---|
| Private create request | At most 65,536 serialized UTF-8 bytes; this check occurs after the existing worker transport parses its JSON |
| Text | Nonblank title up to 120 Unicode scalar values; description up to 20,000; text is preserved |
| Idempotency key | Nonempty, at most 128 UTF-8 bytes, no control characters |
| Sources | Empty only until authorized-source integration |
| Retained create receipts | At most 256 per package, 1,024 per board/profile and 1 MiB serialized ledger |
| At capacity | Existing same-key results remain replayable; new creates report `RESOURCE_LIMIT`; no TTL or automatic receipt eviction |

The ledger quotas are retained-data policies, not transport/decode allocation or total-memory
bounds. The legacy worker framing remains unchanged and trusted-only. C01c must publish applicable
limits through the canonical contract/kit when exposing this operation; R02 owns isolated framing.

## Verification and retained failures

All six initial behavioral tests failed before implementation because the worker had no create
operation: `/tmp/nooki-c01b2-red.log`. The final ten tests cover:

1. Real board-file item/receipt readback, native provenance, no persisted bearer handle, and no
   execution state or agent start after worker tick.
2. Canonical replay, changed-input conflict, host restart with a fresh grant, and replay after card
   deletion without recreation or receipt replacement.
3. Stale whole-board saves fail without changing disk; valid user edits preserve provenance and
   advance revision/token while retaining the original receipt.
4. A staging-path directory injects pre-rename failure; retry commits exactly one item and receipt.
5. Wrong caller/revoked handles fail for new creates and existing receipt replay.
6. Unknown fields, invalid content and multibyte input exceeding the serialized ceiling are refused;
   unapproved references are not read.
7. Mode 0300 on the isolated data directory permits rename but denies the directory-open durability
   step. Creation and repeated replay report `OUTCOME_UNKNOWN`; after permissions recover, replay
   returns the committed original without changing the board. This is an actual filesystem fault,
   not a simulated success stub.
8. Package-scoped keys, per-package/aggregate retained-ledger limits, byte-limit rejection during
   backup validation, and preservation/replay of old outcomes at capacity. Capacity fixtures populate
   valid retained records directly; they do not claim 1,024 independently executed creates.
9. The actual `app --task-worker` process handles three concurrent same-key IPC requests as one
   create. A second request's client drops its reply; after the effect is observed and that worker
   is terminated/reaped, a replacement returns its original result. Renderer access to the private
   create/management paths fails while ordinary read still works.
10. A partial first socket request holds the real worker while another full create request is queued.
    Native revocation happens before releasing the first connection; the queued request is rejected
    and no board file is created.

Self-review found that replay initially acknowledged a visible receipt without repeating the failed
directory sync. The added regression failed (`/tmp/nooki-c01b2-replay-red.log`) before the correction.
Independent bounded review found no additional substantive issues, including a follow-up review of
the durability amendment.

The first full native run observed a transient pre-effect task-data lock refusal in the direct-owner
test (`/tmp/nooki-c01b2-native.log`). It is retained as a failed run, not a pass. The test driver now
retries only that exact busy response, with a three-second deadline; every other error remains
visible. The cause of the transient contention was not independently established. Final runs below
pass; no production busy error was suppressed or translated into success.
